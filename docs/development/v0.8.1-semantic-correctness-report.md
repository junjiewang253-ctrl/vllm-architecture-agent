# v0.8.1 Semantic Correctness Report

## 1. v0.8 Semantic Errors

v0.8 already produced six deterministic pages, but several relationships were too loosely grounded. Some direct relationships were supported by imports or broad line-level hints instead of structured behavior facts. The Adapter and Weight views also blurred configuration access, module composition, parallelism, and checkpoint loading into relationships that looked more certain than the single `hy_v3.py` file could prove.

The main corrected issues were:

- HPC Attention input now comes from `QKV Projection.qkv_out`, not from a Q stream.
- Q/K RMSNorm is explicitly optional under `self.use_qk_norm`; Q and K also have optional bypass edges to RoPE.
- V bypasses Q/K RMSNorm and goes directly to the Attention core.
- KV Cache read into vLLM Attention is marked `external`, because the read occurs inside the external Attention implementation rather than in `hy_v3.py`.
- Decoder stack has distinct `hidden_out` and `residual_out` ports.
- Decoder Detail models `residual is None` initialization without reintroducing large fake Residual Handoff module nodes.
- Expert Bias is a construction dependency, not a runtime tensor edge.
- EPLB metadata is parallel/construction metadata, not runtime tensor input.
- MoE restore shape is represented from `final_hidden_states.view(orig_shape)`.
- Adapter configuration direction is `VllmConfig -> model_config.hf_config -> HYV3Config`, not `HYV3Config -> VllmConfig`.
- Weight loading is split into wrapper and model entrypoints instead of one blended flow.

## 2. Extractor Problems

The previous source-analysis schema had useful v0.8 fields, but it did not provide enough structured facts to prove semantic coverage. It preserved line numbers and some hints, yet important details were still implicit:

- only `forward` had rich control-flow serialization;
- nested `_filter_weights` was not modeled as a first-class method flow;
- call arguments and kwargs were not consistently structured;
- generic assignments were missing;
- generic branches such as `residual is None`, `self.use_qk_norm`, `router.gate`, and `is_pp_missing_parameter(...)` were not fully inventoried;
- weight loading flow stages could not separate `HYV3ForCausalLM.load_weights` from `HYV3Model.load_weights`;
- old `weight_mappings` and `weight_loading_hints` did not carry stable fact IDs.

v0.8.1 upgrades Source Analysis to 0.3 and adds stable fact IDs across structured facts.

## 3. Builder Problems

The v0.8 builder was deterministic, but several edges still depended on broad evidence and page-level interpretation. v0.8.1 changes the builder so IR evidence prefers `fact_ids`, direct evidence must point to structured behavior facts, and external behavior is no longer labeled direct.

The builder now emits Architecture IR 0.6, keeps `source_fact_ids`, records `weight_loading_entrypoints`, and generates seven pages:

- Model Overview
- Decoder Layer Detail
- Attention Detail
- MoE Detail
- vLLM Adapter Integration
- Parallelism
- Weight Loading

## 4. View Problems

The Diagram View layer in v0.8 planned six pages. It also had route and lane presets for the combined Parallelism & Weight Loading page. v0.8.1 updates view planning so the old combined page is removed and the two concerns become independent pages.

The View validator now rejects legacy combined pages and checks that the View does not change edge kind or hide required correctness labels on conditional paths.

## 5. Source Analysis 0.3 Design

Source Analysis 0.3 preserves all previous fields and adds:

- `methods`
- `method_control_flows`
- `calls`
- `assignments`
- `branches`
- `returns`
- `config_accesses`
- `parallelism_facts`
- `weight_loading_flows`
- `semantic_facts`

These fields do not perform cross-file type inference. They only serialize facts available from `hy_v3.py`.

## 6. Stable Fact ID Design

Stable IDs use the pattern:

```text
fact:<qualified-name>:<line>:<kind>:<slug>
```

Examples:

```text
fact:HYV3Attention.forward:343:call:self.hpc_rope_norm
fact:HYV3DecoderLayer.forward:417:branch:residual_is_none
fact:HYV3Model.load_weights:580:assignment:name
```

IDs are derived from class, method, source line, fact kind, and a stable slug. They do not depend on Python object identity, traversal memory addresses, or random values.

## 7. Method Control Flow Design

The extractor now serializes important methods, including:

- `__init__`
- `forward`
- `compute_logits`
- `load_weights`
- `get_expert_mapping`
- `update_physical_experts_metadata`
- `embed_input_ids`
- nested `_filter_weights`

Each method control flow records owner class, method name, qualified name, source range, parameters, and a body made of assignment, call, branch, loop, return, yield, continue, break, assert, raise, and expression facts.

## 8. Weight Loading Flow Design

Weight loading is now represented with two separate entrypoints:

- `HYV3ForCausalLM.load_weights`
- `HYV3Model.load_weights`

The wrapper flow records the nested `_filter_weights` boundary, speculative layer filtering, tied `lm_head` filtering, `AutoWeightsLoader` construction, and loader call.

The model flow records `stacked_params_mapping`, `params_dict`, `get_expert_mapping`, iteration over weights, tied embedding skip, FP8 scale remap, stacked dispatch, expert dispatch, bias skip, PP missing filter, router rename, parameter loader dispatch, default loader fallback, collection, and return.

This prevents the diagram from pretending that all model weights pass through the wrapper `AutoWeightsLoader`.

## 9. Semantic Inventory Design

`build_semantic_inventory.py` converts `semantic_facts` into a coverage inventory. Facts are categorized as:

- `model_structure`
- `runtime_flow`
- `construction`
- `configuration`
- `tensor_parallel`
- `pipeline_parallel`
- `expert_parallel`
- `checkpoint_loading`
- `capability`
- `external_boundary`

Each fact is marked `required`, `optional`, `informational`, or `excluded`. Required facts must be consumed by IR evidence or explicitly unresolved by coverage validation.

## 10. Semantic Coverage Validator Design

`validate_semantic_coverage.py` consumes source-analysis, semantic inventory, and Architecture IR. It writes:

```text
outputs/<model>-semantic-coverage.json
```

Each relevant fact receives one status:

- `consumed`
- `excluded`
- `unresolved`

The v0.8.1 run produced:

- required facts: 154
- consumed facts: 82
- excluded facts: 306
- unresolved facts: 110
- orphaned facts: 0

The validator also ensures IR evidence does not reference unknown fact IDs.

## 11. Seven-Page Semantic Corrections

Model Overview keeps the top-level inference flow and uses distinct Decoder Stack `hidden_out` and `residual_out` ports feeding Final Residual Add.

Decoder Layer Detail removes the old handoff circles and models residual as a lower lane. It adds `residual_initialization` from the `residual is None` branch.

Attention Detail now branches HPC from `qkv_projection.qkv_out`; fallback splits Q/K/V locally; Q/K Norm has optional bypass; V never enters Q/K Norm; KV Cache read is external.

MoE Detail includes Flatten Tokens, GateLinear, Router Logits, FusedMoE, Expert Bias, EPLB Metadata, Shared Experts, Restore Original Shape, and Output. Expert Bias is construction, and EPLB is parallel metadata.

Adapter Integration now uses config-access direction from `VllmConfig` to concrete config nodes, shows `HYV3ForCausalLM` containing `HYV3Model`, and expands concrete execution components.

Parallelism has independent TP, PP, and EP lanes.

Weight Loading separates wrapper and model load flows, shows FP8 remap before mapping dispatch, and applies PP filtering to stacked, expert, and regular paths.

## 12. Evidence Types

Architecture IR 0.6 evidence supports:

- `direct`: structured source behavior, such as assignment, call, branch, or return facts;
- `derived`: a diagram abstraction derived from source facts, with fact IDs or a derivation note;
- `external`: behavior known to occur inside a referenced external component;
- `unresolved`: facts that cannot be proven from the single file.

Runtime and weight-loading behavior cannot be backed only by import facts.

## 15. Core Functions

`extract_architecture.extract_architecture(source_path)` reads one Python file and returns Source Analysis 0.3. It uses the standard `ast` module, preserves line numbers, and emits stable fact IDs.

`serialize_call(...)` records call target, receiver, positional args, kwargs, references, source text, assignment targets, and resolved collections when available.

`serialize_statements(...)` converts AST statements into method-control body facts and now includes stable IDs for assignments, calls, branches, loops, returns, and control statements.

`ArchitectureVisitor._collect_weight_loading_flow(...)` builds per-entrypoint weight-loading stages from structured body facts.

`build_semantic_inventory.build_semantic_inventory(source_analysis)` classifies source semantic facts and assigns relevance.

`build_architecture_ir.build_architecture_ir(data)` creates Architecture IR 0.6 pages from Source Analysis 0.3. It records source fact IDs and weight-loading entrypoints.

`validate_architecture_ir.validate_architecture_ir(data)` validates schema version, page/node/edge integrity, ports, phase/kind compatibility, evidence types, direct evidence fact IDs, and semantic edge constraints.

`validate_semantic_coverage.validate_semantic_coverage(source_analysis, inventory, ir)` writes the coverage report and ensures orphaned required facts are zero.

`build_diagram_view.build_diagram_view(ir)` turns IR into presentation planning without changing semantics.

`layout_diagram.build_layout_plan(view)` assigns deterministic boxes and routed waypoints.

`render_drawio.render_drawio(view, layout_plan)` writes Draw.io XML from the view and layout plan.

## 22. External and Unresolved Boundaries

The following remain intentionally outside direct proof:

- vLLM Attention internal KV cache read behavior;
- FusedMoE internal communication or expert dispatch kernels;
- AutoWeightsLoader internals;
- LoRA runtime internals;
- torch.compile internals;
- Scheduler, Worker, EngineCore, request batching, and sampling.

These are either not drawn or represented as external/unresolved boundaries.

## 23. Current Limitations

The implementation still focuses on HY V3 and the existing source-analysis sample. The layout remains deterministic and page-specific rather than a general DAG solver. Coverage is conservative: required facts not directly drawn may be marked unresolved with a reason instead of forcing every fact into a diagram node.

The extractor still does not perform cross-file type inference, so external component internals cannot be proven from `hy_v3.py`.

## 24. v0.9 Suggestions

Suggested next work:

- improve semantic inventory classification to reduce unresolved-but-handled facts;
- add richer source-grounded notes for external boundaries;
- add more visual regression fixtures for edge routing;
- add a dedicated Weight Mapping Detail page if users need deeper checkpoint analysis;
- extend coverage tests to another model only after HY V3 semantics remain stable;
- introduce optional, still dependency-free layout heuristics for dense adapter pages.
