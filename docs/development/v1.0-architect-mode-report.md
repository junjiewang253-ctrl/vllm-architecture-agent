# v1.0 Architect Mode Report

## 1. Why Move From Rule-Based Diagrams to Agent Architect Mode

Earlier versions proved that the repository could extract source facts, build
Architecture IR, validate evidence and render deterministic Draw.io files. That
pipeline was useful, but it still behaved like code visualization: AST facts
became nodes and edges with limited architectural interpretation.

v1.0 introduces a separate Architecture Concept Layer. The scripts continue to
define the trusted boundary: what facts exist, which evidence IDs are valid and
which external component internals cannot be claimed. The Agent becomes an
Architect: it groups facts into higher-level concepts, chooses abstraction
level, plans pages and writes a mentor-readable explanation.

## 2. Source Fact Graph Design

`build_source_fact_graph.py` converts Source Analysis 0.3 into
`source-fact-graph.json`.

The graph contains:

- `facts`: normalized source-backed facts with stable IDs, summaries, owner
  class/method and evidence.
- `relations`: conservative fact-level relations such as `contains`,
  `constructs`, `implements`, `parallelizes` and `maps_to`.

For HY V3, the generated graph contains 564 fact nodes and 134 fact relations.
The graph does not create architecture concepts. It only says what the input file
proves.

## 3. Concept Layer Design

`run_architect_review.py` creates `architecture-design.json`. In the interactive
Skill workflow, this is the Agent Architect decision point; the script provides a
validated, reproducible architect pass for CI and the HY V3 experiment.

Each concept includes:

- stable `concept:` ID;
- fixed concept type;
- human title;
- purpose;
- implementation symbols;
- source fact evidence;
- confidence.

HY V3 currently produces 11 concepts, including Tensor Parallel QKV Projection,
Q/K Positional Processing, KV Cache Boundary, MoE Execution Strategy, Parallel
Execution Strategy, Checkpoint Adaptation and vLLM Integration Boundary.

## 4. Agent Permission Boundary

The Agent may aggregate low-level facts into high-level architecture concepts,
decide whether capabilities should be badges or nodes, and decide page purpose.

The Agent may not:

- create a concept without fact evidence;
- modify source facts;
- mark external component internals as direct local behavior;
- directly generate Draw.io XML;
- skip validators.

`validate_architecture_quality.py` enforces the most important constraints:
concept evidence exists, relationships cite evidence, pages have purpose,
concepts are not isolated, and boundaries have explicit allowed claims.

## 5. Architecture Design Generation

The HY V3 design groups facts into concepts rather than rendering every call.
For example, facts around `QKVParallelLinear`, attention construction and TP
symbols become the concept “Tensor Parallel QKV Projection.” Facts around
`FusedMoE`, expert metadata and shared experts become “MoE Execution Strategy.”

This preserves traceability while producing a diagram that a mentor can read as
architecture, not a code dependency graph.

## 6. View Planning

`view_planner.py` converts `architecture-design.json` into
`architecture-view.json`. A page is defined by the question it answers and the
concepts it shows. The View keeps concept IDs, display labels, routing hints,
annotations and page purposes.

The v1.0 pages are:

- HY V3 vLLM Adapter Overview;
- Transformer Execution Flow;
- Attention Implementation;
- MoE Execution Strategy;
- Parallel Execution Strategy;
- Checkpoint Adaptation;
- vLLM Integration Boundary.

## 7. Renderer Changes

`layout_diagram.py` now accepts Architecture View schema `1.0` in addition to
legacy Diagram View schema `0.1`. When no fixed preset matches the concept node
IDs, it uses a deterministic dynamic grid layout based on the visible concepts
and preferred sizes.

`render_drawio.py` already rendered View objects rather than raw IR. Its role is
unchanged in spirit: consume View plus Layout Plan and emit stable Draw.io XML.
It does not decide architecture semantics.

## 8. Semantic Boundary

`build_boundary_report.py` generates `boundary-report.json`. HY V3 reports three
external boundaries:

- vLLM Attention;
- FusedMoE;
- AutoWeightsLoader.

The allowed claims are intentionally narrow. The report does not say these
components' internals were analyzed; it only records how the model file
constructs or delegates to them.

## 10. v0.9 Comparison

v0.9.1 focused on Review/Patch correctness around Architecture IR and Diagram
View. v1.0 keeps that trusted foundation but adds a higher architecture layer so
the final artifact explains concepts and boundaries rather than only rendering
semantic nodes and edges.

## 11. Current Limits

- The Architect Review is still conservative and HY V3-focused in its concept
  vocabulary.
- External vLLM components are not recursively analyzed.
- The dynamic concept layout is intentionally simple and not a general DAG
  layout engine.
- The project has not yet been validated on Llama, Qwen, Mixtral or other vLLM
  adapters.

## 12. Next Multi-Model Validation Plan

v1.1 should run the same Source Fact Graph and Concept Layer against additional
model adapters, compare concept coverage, and refine architecture concepts that
generalize across model families without adding hard-coded model-specific rules.
