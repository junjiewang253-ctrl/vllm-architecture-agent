# v2.0 Agent-Native Refactor Report

Version: 2.0.0  
Name: Agent-Native vLLM Architecture Skill

## 1. Why v1.2 Was Over-Engineered

The v1.2 workflow proved that source facts, intermediate graphs, patches,
validators, layout plans and deterministic rendering could be chained together.
It also made the Skill feel more like a compiler than an Agent Skill. A normal
user wanted: read a vLLM model adapter, explain it, and draw a useful diagram.
Instead, the default path produced many internal JSON artifacts and pushed the
Agent into a narrow role around precompiled structures.

The largest issue was not any one script. It was the overall shape: page choice,
architecture explanation and visual design were being represented as mechanical
compilation products. That made the system brittle for unknown model categories.

## 2. Agent Skill Lightweight Principle

v2.0 restores the Agent as the task subject.

Scripts now perform mechanical operations:

- resolve a model target;
- parse registry mappings;
- index a target Python file;
- classify candidate capabilities;
- validate the Agent-authored plan and evidence;
- validate Draw.io file structure;
- scan a models directory without crashing.

Codex performs the judgment:

- which source files to read;
- what the architecture means;
- which pages to create;
- which facts deserve nodes, badges, annotations or boundaries;
- how to draw the diagram through Draw.io MCP;
- how to revise the first PNG.

## 3. Subtractive Refactor Goal

This is intentionally not another layer on top of v1.2. The default workflow
removes Architecture IR, Concept Graph rendering, Design Graph compilation,
View Graph compilation, layout plans, review patches, coverage matrices and
review locks.

Those systems are preserved in `legacy/compiler-pipeline-v1/` for research
history, but they are not part of the default Skill or CLI.

## 5. New Default Workflow

The v2.0 workflow is:

```text
target file or registry architecture
-> resolve_model_target.py
-> collect_source_context.py
-> source-context.json
-> Codex source traversal
-> architecture-plan.json + evidence.json
-> validate_architecture_plan.py + validate_evidence.py
-> Draw.io MCP drawing
-> PNG visual review
-> validate_drawio.py
-> architecture.drawio + images + report.md
```

Default output is now limited to seven classes of files:

- `source-context.json`;
- `architecture-plan.json`;
- `evidence.json`;
- `architecture.drawio`;
- `report.md`;
- `visual-review.md`;
- `images/`.

## 6. Registry Resolution

`resolve_model_target.py` statically parses:

```text
vllm/model_executor/models/registry.py
```

It extracts static entries shaped like:

```python
"ArchitectureName": ("module_name", "ClassName")
```

It also expands static dictionary merge entries in `_VLLM_MODELS`. It does not
import vLLM, torch, transformers or CUDA-dependent code. Registry parsing uses
`utf-8-sig` so files generated by Windows tools with a BOM still parse.

## 7. Source Context

`collect_source_context.py` is an indexer, not an architecture interpreter.

It records:

- target metadata;
- classification candidates;
- classes and methods;
- imports;
- `self.<attribute> = Constructor(...)` assignments;
- control-flow landmarks;
- weight mapping hints;
- registry info;
- capability signals;
- related file candidates;
- traversal defaults and warnings.

It deliberately does not produce final pages, final nodes, final edges or
coordinates.

## 8. Codex Source Traversal Strategy

The Skill now instructs Codex to:

1. read the target file first;
2. use Source Context as an index;
3. follow related files only when they support a diagram claim;
4. stop at stable external boundaries;
5. record files read and traversal stops in the plan and report.

Default traversal budget:

- maximum depth: 3;
- default related files: 20;
- suggested maximum: 30.

## 9. Dynamic Page Selection

Scripts no longer decide page sets. Codex selects pages from source evidence.

Recommended pages include:

- Model Overview;
- Adapter Boundary;
- Decoder or repeated block detail;
- Attention;
- MoE;
- Multimodal data path;
- Pooling or embedding;
- Classification head;
- Hybrid or recurrent block;
- Parallel Strategies;
- Weight Loading;
- Quantization;
- LoRA;
- External backend boundary.

No MoE evidence means no MoE page. A helper file should not receive a full
model architecture diagram.

## 10. Architecture Plan

`architecture-plan.schema.json` defines the Agent-authored plan. It includes:

- model name;
- target file;
- model categories;
- files read;
- pages;
- global boundaries;
- omissions;
- unresolved items.

Each page states:

- page title;
- engineering question;
- purpose;
- view pattern;
- scope;
- claim IDs;
- main story;
- secondary topics;
- external boundaries;
- visual decisions;
- detail budget.

The plan does not contain Draw.io XML or exact coordinates.

## 11. Evidence Policy

`evidence.schema.json` and `validate_evidence.py` support:

- `direct`;
- `derived`;
- `external`.

Direct claims must cite concrete source lines and cannot rely only on import
lines. Derived claims require at least two evidence entries. External claims
must explain what the local file proves and where the boundary begins.

## 12. Draw.io MCP Drawing

The deterministic renderer is no longer default. Codex uses Draw.io MCP to draw
pages from the validated plan.

The Skill requires:

- page names matching the plan;
- runtime data flow only for runtime relationships;
- configuration, capability, parallelism and checkpoint loading not drawn as
  tensor flow;
- explicit external boundaries;
- implementation names in subtitles;
- no source line clutter in diagram nodes;
- white opaque background.

## 13. Visual Review

After the first PNG export, Codex writes `visual-review.md`. It checks:

- page purpose clarity;
- text overlap;
- edge-through-node problems;
- long or confusing lines;
- repeated labels;
- whitespace;
- density;
- concept-card pages.

At most two visual revision rounds are allowed.

## 14. Lightweight Validators

v2.0 validators are intentionally narrow:

- `validate_architecture_plan.py`: schema-like plan checks and capability/page
  conflicts;
- `validate_evidence.py`: file paths, line ranges, evidence confidence rules
  and import-only direct evidence;
- `validate_drawio.py`: XML structure, pages, cell IDs, geometry, white
  background and `html=0`;
- `scan_models_directory.py`: prepare-like scan across model files with
  per-file warnings rather than uncaught failures.

They do not enforce fixed pages or fixed model-specific node IDs.

## 15. Multi-Model Compatibility

The pattern registry in `src/vllm_architecture_agent/patterns.py` returns only
candidate categories. It recognizes common constructor and capability terms such
as embeddings, attention, parallel projections, normalization, FFN, MoE,
pooling, recurrent/state-space blocks, loaders and capabilities.

It does not contain final page templates or fixed coordinates.

## 18. v1.2 and v2.0 Code/Output Comparison

v1.2 default output included source analysis, semantic inventory, source fact
graph, architecture concept, boundary report, architect brief, architecture
design, architecture view, layout plan, layout metrics, Draw.io and report.

v2.0 default output keeps only Source Context, Agent-authored Plan, Evidence,
Draw.io, report, visual review and exported images.

The old pipeline archive contains 162 files. The new canonical Skill contains
six scripts, three schemas, five references, one asset and one SKILL file.

## 20. Current Limitations

- Real full-directory vLLM scan was not run in this environment.
- Codex drawing quality depends on the active Agent following the Skill and
  Draw.io MCP workflow.
- Validators check structure and evidence boundaries, not fixed semantic node
  IDs.
- The Source Context classifier is intentionally conservative and returns
  candidates for Agent review.
- External vLLM component internals are not analyzed unless Codex explicitly
  reads the corresponding local files.

## 21. Claude Code Adaptation

Future Claude Code or other Agent packaging should reuse the same v2.0 Skill
rules, scripts, schemas and references. Agent-specific wrappers belong under
`integrations/`, not inside the canonical Skill logic.
