# v1.2 Current State Audit

This audit was written before the v1.2 code changes, as required by the task
brief. It records the real v1.1 behavior rather than the intended architecture.

## 1. Current Architect Mode Flow

`vllm-arch run --mode architect` currently performs the following steps inside
`src/vllm_architecture_agent/cli.py`:

1. `extract_architecture.py`
2. `build_semantic_inventory.py`
3. `build_source_fact_graph.py`
4. `run_architect_review.py`
5. `run_design_architect.py`
6. `build_view_from_design.py`
7. `build_boundary_report.py`
8. `validate_architecture_quality.py`
9. `validate_architecture_view.py`
10. `apply_view_layout.py`
11. `render_drawio.py`
12. `build_mentor_report.py`

This is one-shot and fully scripted. It does not pause for a Codex-authored
Architecture Design file.

## 2. `run_architect_review.py` Agent Involvement

`run_architect_review.py` does not call an Agent or read an Agent-authored
review. It builds a fixed Architecture Concept Graph in Python. The script uses
string matching over Source Fact Graph facts, then emits eleven concepts and a
fixed set of relationships and suggested views.

This is useful as a deterministic baseline, but it should not be described as
an Agent-authored design step.

## 3. `run_design_architect.py` Hard-Coded Content

`run_design_architect.py` is a Python template. It hard-codes:

- concept IDs such as `concept:hyv3_vllm_adapter`,
  `concept:tensor_parallel_attention_projection`,
  `concept:moe_execution_strategy`, and `concept:checkpoint_adaptation`;
- six pages: `model_overview`, `attention`, `moe`, `checkpoint`,
  `parallel_strategy`, and `vllm_boundary`;
- page questions and purposes;
- every node ID, label, role, row, column, implementation and port;
- every edge ID, kind/source/target/ports/labels;
- HY V3-specific story structure including QKV, HpcRopeNorm, FusedMoE,
  AutoWeightsLoader, and the local/external boundary page.

This means architect mode currently creates a baseline design template and does
not require the active Codex Agent to design the pages.

## 4. `build_view_from_design.py` Is Mostly Copying

`build_view_from_design.py` currently:

- checks only `schema_version == "0.1"` and
  `design_graph_type == "architecture_design_graph"`;
- copies each design node to a view node;
- maps `role` to `visual_role`;
- copies each edge to a view edge;
- copies groups, lanes, annotations and strategies;
- adds a fixed legend.

It does not compile page patterns, convert capabilities into badges, convert
containment into containers, lower-priority dependencies into annotations, or
generate view-specific regions/lane constraints. It is a mechanical projection.

## 5. Current Design Schema Is Too Loose

`design/architecture-design.schema.json` is version `0.1` and requires only:

- top-level `schema_version`, `model_name`, `pages`;
- page `id`, `title`, `question`, `purpose`, `main_flow`, `nodes`, `edges`,
  and `external_boundaries`.

Most important structures are untyped arrays, including `nodes`, `edges`,
`branches`, `groups`, `lanes`, `annotations`, and `strategies`.

The schema also uses `additionalProperties: true` at the root and page level.
It does not strictly define node semantic kind, role, phase, ports, edge kinds,
display policy, route hints, primary story, coverage or author metadata.

## 6. Layout Uses Row/Column Grid Logic

`layout_diagram.py` still contains `_dynamic_boxes()`, which lays out
Architecture View pages using row/column hints when present:

- nodes can provide `layout.row` and `layout.col`;
- otherwise the layout uses a simple grid;
- page content is distributed uniformly inside fixed page dimensions.

This produces deterministic output, but it does not understand page narrative,
branch/merge structure, residual lanes, strategy panels, mapping dispatch
lanes, or local/external boundary columns as first-class layout patterns.

## 7. `_manual_route()` Has Stale Page IDs

`layout_diagram.py` still contains `_manual_route(page_id, edge_id)`.

It has hard-coded overrides for:

- `attention_detail`
- `weight_loading`

Current v1.1 Architecture View page IDs are:

- `model_overview`
- `attention`
- `moe`
- `checkpoint`
- `parallel_strategy`
- `vllm_boundary`

Therefore the current manual routes do not apply to v1.1 architect pages.
They are stale and tied to older Diagram View/IR page IDs.

## 8. Architect Mode Omits Validators

Architect mode currently validates:

- Architecture quality;
- Architecture View.

It does not run:

- a strict Architecture Design validator;
- `validate_drawio.py`;
- `validate_visual_layout.py`;
- a metrics-producing visual validation step;
- stale source hash checks on the Design file.

This means architect mode can produce Draw.io without the same post-render
guardrails as the v0.9.1 reviewed pipeline.

## 9. Current Six-Page Semantic Problems

The current v1.1 pages are better than raw concept cards, but still incomplete
relative to the v1.2 target:

- There is no Decoder Block page.
- Model Overview does not show Final Residual Add explicitly.
- Overview lacks the PP non-first/non-last/last rank side branches.
- Attention shows Q/K/V and HPC/fallback, but Design schema cannot enforce
  branch/merge correctness or external KV-cache-read boundaries.
- MoE shows `FusedMoE -> Experts -> Output`, which can imply experts happen
  after FusedMoE rather than inside its container.
- Checkpoint is a single mapping flow, not the two separate
  `HYV3ForCausalLM.load_weights` and `HYV3Model.load_weights` lanes.
- Parallel Strategy has a shared note node; this is better than TP->PP->EP but
  still not a true three-panel matrix.
- Boundary delegation is not specific enough for all local class/method to
  external runtime relationships.

## 10. Current Tests

The test suite currently has 103 passing tests. Architect-related tests in
`tests/test_architect_mode_v10.py` verify:

- Source Fact Graph has QKV and tensor-parallel relations;
- concepts have evidence;
- Attention View contains QKV, Q/K/V Split, HPC Fused Processing, Optional QK
  Norm, KV Cache Boundary and vLLM Attention Backend;
- Architecture Design has an attention question, main flow, HPC/fallback
  branches and an external boundary;
- View pages have at least three nodes and are not concept-card-only;
- MoE and Checkpoint pages contain certain labels;
- boundary report includes vLLM Attention, FusedMoE and AutoWeightsLoader;
- validators accept the artifacts;
- CLI architect mode writes expected output files.

These tests mostly verify existence of labels and files. They do not prove:

- an active Codex Agent authored the Design;
- architect mode refuses to run without an Agent-authored Design;
- strict schema validation catches unknown or missing core properties;
- edge ports and phase compatibility;
- each `view_kind` uses a dedicated layout strategy;
- visual metrics such as no edge-node intersections, text overflow, crossing
  thresholds, panel equality, branch merge alignment, or boundary column
  alignment;
- `simple_model` produces a different page set without MoE/EP pages;
- production scripts avoid hard-coded HY V3 node lists.

## Audit Conclusion

v1.1 has the right conceptual layering, but architect mode is still a scripted
template pipeline. v1.2 must introduce a real two-stage workflow where scripts
prepare source-grounded context and the current Codex Agent authors the strict
Architecture Design JSON before finalization.
