# v1.0.2 View Architect Report

## 1. Why Concept Graph Cannot Draw Directly

v1.0 proved that source facts can be grouped into architecture concepts, but
concepts are not diagrams. Rendering concepts directly produces cards such as
“Tensor Parallel QKV Projection” or “MoE Execution Strategy.” Those cards explain
meaning, but they do not show how data enters, which component transforms it,
where runtime flow happens, how checkpoint weights map, or where vLLM external
boundaries begin.

v1.0.2 therefore makes Architecture View Graph the renderer input.

## 2. View Graph Design

`architecture-view.json` schema `0.1` describes pages, view nodes, view edges,
groups, lanes, annotations, boundaries and legend.

View node types are:

- `component`
- `data`
- `process`
- `storage`
- `boundary`
- `capability`
- `annotation`
- `group`

View edge types are:

- `runtime_flow`
- `dependency`
- `mapping`
- `parallel`
- `delegation`
- `boundary`
- `annotation`

Every core node carries both `concept_refs` and `fact_refs`, so the graph is
human-readable without losing source traceability.

## 3. Agent View Architect Workflow

`run_view_architect.py` reads `architecture-concept.json` and
`source-fact-graph.json`. It decides how a human should read the architecture:
which concepts become components, which become capabilities, which become
boundary notes, and which edges are runtime, mapping, parallel or delegation.

Renderer does not read concepts or invent nodes. It only renders View Graph.

## 4. Attention View Design

The Attention page now contains actual architecture flow:

- Hidden States
- QKV Projection
- HPC Fused Processing
- Q/K/V Split
- Q Path
- K Path
- V Path
- Optional QK Norm
- RoPE Processing
- KV Cache Boundary
- vLLM Attention Backend
- Output Projection
- Attention Output

It shows both paths:

- HPC path: QKV Projection -> HPC Fused Processing -> vLLM Attention Backend.
- Fallback path: Q/K/V Split -> Q/K streams -> Optional QK Norm -> RoPE ->
  vLLM Attention Backend, while V reaches the backend separately.

KV Cache remains a boundary, not a direct local implementation claim.

## 5. MoE View Design

The MoE page now shows:

Hidden States -> Router -> Top-K Routing -> FusedMoE -> Routed Experts -> Output.

Shared Experts are shown as optional dependency, and Expert Parallel is shown as
a parallel capability into FusedMoE.

## 6. Checkpoint View Design

The Checkpoint page now shows:

- HF Checkpoint;
- Weight Name Processing for filter/rename;
- Packed Mapping;
- q/k/v -> qkv_proj;
- gate/up -> gate_up_proj;
- expert weights -> Expert Params;
- Loader Dispatch;
- vLLM Parameters.

These edges use `mapping`, not runtime flow.

## 7. Adapter Boundary View Design

The boundary page separates local model adapter behavior from imported vLLM
components:

- Local: HYV3ForCausalLM, HYV3Model, Weight Mapping, Parallel Logic.
- External: vLLM Attention Backend, FusedMoE Runtime, AutoWeightsLoader.
- Middle edges use `delegation` or dependency, not fake runtime flow.

## 8. Validator

`validate_architecture_view.py` rejects:

- concept-card-only pages;
- pages with fewer than three nodes;
- pages with only annotation edges;
- missing runtime flow on major runtime pages;
- missing Attention QKV/Q-K-V/KV Cache/backend nodes;
- missing MoE Router/FusedMoE/Experts/EP nodes;
- missing Checkpoint HF Weight/Mapping/vLLM Parameter nodes;
- external boundary -> local runtime flow claims.

## 9. v1.0 and v1.0.2 Comparison

v1.0:

Concept Graph -> Draw.io.

v1.0.2:

Concept Graph -> Architecture View Graph -> Draw.io.

The result is no longer a wall of concept cards. The View Graph contains runtime
flow, mapping flow, component interaction, parallel capabilities and external
boundaries.

## 10. Current Limits

- View Architect remains conservative and is still validated primarily on HY V3.
- Layout is deterministic but not a general automatic graph layout engine.
- External vLLM internals remain boundaries.
- Multi-model validation is still needed before claiming broad model coverage.
