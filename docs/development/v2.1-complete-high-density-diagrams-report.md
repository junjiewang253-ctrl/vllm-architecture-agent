# v2.1 Complete High-Density Diagrams Report

## 1. v2.0 Issues

v2.0 intentionally removed the earlier compiler pipeline and made Codex the diagram architect. That direction was right, but the lightweight Source Context was too shallow for complete review. It indexed common top-level classes and important methods, but it did not prove that every class, method, module function, branch, and weight-loading structure in the target file had been discovered. The plan also recorded pages, not a target-file review manifest, so a diagram could pass while silently omitting relevant source structure.

## 2. Why Not Add Many Detail Pages

The v2.1 goal is complete but readable diagrams. Adding one page per class or method would make the result hard to review and would move the tool back toward code visualization. v2.1 keeps the Agent-native model and asks Codex to cluster details into 3 to 5 composite pages using containers, parameter panels, embedded subgraphs, variant tables, strategy panels, and mapping trees.

## 3. Few-Page High-Density Design

Full models default to four pages and are limited to five. Helper or boundary-only files can produce one or two pages. The plan schema now includes a `page_budget` and every page must contain one or more `detail_regions` tied to source item IDs and evidence claims.

## 4. Recursive Class/Method Catalog

`collect_source_context.py` now uses a recursive AST catalog visitor. It indexes:

- all top-level classes;
- all nested classes;
- all class methods and async methods;
- all module-level functions and async functions;
- branches and match statements;
- loops;
- calls;
- module assignments;
- weight-loading and mapping landmarks.

Important methods are no longer a filter. They only influence the mechanical `importance_candidate`.

## 5. Stable ID

Source objects receive stable IDs based on qualified names and source lines:

- `class:<qualified_name>:<line>`
- `method:<qualified_name>:<line>`
- `function:<name>:<line>`
- `branch:<owner_qualified_name>:<line>:<ordinal>`
- `loop:<owner_qualified_name>:<line>:<ordinal>`
- `mapping:<owner_qualified_name>:<line>:<ordinal>`
- `capability:<capability_name>`

These IDs do not depend on object identity or runtime imports.

## 6. Source Coverage

The Source Context now includes `source_coverage` with AST counts and catalog counts. The collector self-checks class, method, and module-function totals before writing output. If counts diverge, the context is downgraded and warnings are emitted.

## 7. Class Review

Architecture Plan 2.1 requires one `class_review` entry for every catalogued class. Each entry records role, status, page references, claim IDs, and a reason. Primary components cannot be silently excluded.

HY V3: 6 class reviews, 0 unreviewed.

## 8. Method Review

Every method receives a `method_review`. Core methods must be rendered in detail or aggregate form, must reference at least one claim, and must map to a page detail region. Trivial methods can be excluded only with a reason.

HY V3: 20 method reviews, all core, 0 unreviewed.

## 9. Coverage Manifest

The manifest covers non-class and non-method structures:

- all high/medium branches;
- all weight mappings;
- all detected capabilities;
- external boundaries.

HY V3: 30 required high/medium branches and all 37 branch entries were reviewed. All 69 mappings and all 10 detected capabilities were covered.

## 10. Detail Region

Every page now has explicit detail regions. A region must name the engineering question it answers and map to source item IDs and evidence claims. Region types include embedded subgraph, component tree, nested container, parameter panel, capability panel, strategy panel, variant table, mapping tree, boundary panel, and callout.

## 11. Architecture Plan 2.1

The plan schema was upgraded to 2.1. It now requires:

- `source_sha256`;
- `detail_level`;
- `page_budget`;
- pages with topics and detail regions;
- class/method/function reviews;
- coverage manifests;
- global boundaries, omissions, and unresolved entries.

Full models are limited to 3 to 5 pages.

## 12. Evidence 2.1

Evidence now requires `source_sha256` and source item IDs per claim. Claims have a phase and confidence:

- direct;
- derived;
- external.

Derived claims require a derivation and at least two evidence entries. External claims require an external boundary explanation.

## 13. Completeness Validator

`validate_architecture_plan.py` now checks source hash alignment, page budget, page/region references, class completeness, method completeness, function completeness, branch/mapping/capability coverage, and evidence claim references. It outputs a coverage summary when run directly.

## 14. Source Hash

The plan and evidence files must match `context.source_sha256`. This prevents reusing a plan after the target source changes.

## 15. Draw.io Region Validation

`validate_drawio.py` remains lightweight. It does not infer semantics from fixed node IDs. It checks XML structure, unique pages, explicit white backgrounds, no `html=1`, valid geometry, exact plan page titles, visible detail-region titles, and optional PNG exports by `export_name`.

## 16. Skill Workflow

`SKILL.md` remains Agent-native and lightweight. It instructs Codex to:

1. run prepare;
2. read the complete target source;
3. use the Source Context as a checklist;
4. fill class/method/function reviews;
5. cover branches, mappings, capabilities, and external boundaries;
6. design 3 to 5 high-density pages;
7. write Evidence;
8. validate before drawing;
9. use Draw.io MCP;
10. export PNG and perform a visual review pass.

The Skill is 307 lines, within the requested 180 to 320 line range.

## 17. HY V3 Four-Page Design

The golden example keeps exactly four pages:

1. `Model Architecture and Execution`
2. `Decoder and Attention`
3. `MoE Architecture and Routing`
4. `Parallelism, Configuration and Weight Loading`

Each page contains multiple detail regions rather than becoming a simple overview or one method per page.

## 18. HY V3 Semantic Corrections

The example fixes the known issues:

- pipeline first/non-first and last/non-last behavior is explicit;
- decoder residual and hidden-state lanes are separated;
- Dense FFN and MoE are construction variants, not a runtime branch;
- Dense FFN internals are shown;
- HPC attention is labelled as a configured implementation;
- HpcRopeNorm receives `qkv`, not a Q stream;
- V bypasses Q/K RMSNorm;
- KV cache read is external vLLM Attention behavior;
- FusedMoE experts are inside the FusedMoE boundary;
- wrapper and model `load_weights` are independent entrypoints;
- model weight loading is a dispatch tree;
- LoRA is a capability marker, not a checkpoint-loading edge.

## 22. v2.0 vs v2.1

v2.0 optimized for Agent-native simplicity but left completeness largely to the human agent. v2.1 keeps that lightweight architecture but adds mechanical source coverage and review completeness checks. It does not reintroduce the old IR, view graph, patch, review-lock, layout-plan, or deterministic renderer pipeline.

## 23. Current Limitations

- The validator checks structural completeness and evidence references, not image-level geometry beyond lightweight Draw.io XML checks.
- Visual quality still depends on Codex and Draw.io MCP review.
- The collector remains a source indexer, not a semantic compiler.
- Exact config values are not inferred without a config file.
- External vLLM components are bounded unless Codex explicitly reads their source.
