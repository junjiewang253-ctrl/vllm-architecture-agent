# v0.9.1 Agent Review Integration Report

## 1. Why Move From Rule-Driven Review to Agent-in-the-Loop

v0.9 introduced review and patch artifacts, but the default Semantic Review and
Visual Review were still generated by deterministic Python scripts. That proved
the artifact shape, but it did not satisfy the design goal: use scripts for
trusted boundaries and use Codex for the architectural judgment that is hard to
encode as rules.

v0.9.1 integrates Codex as the active reviewer in the VSCode Codex session. The
important correction in this pass is that the default Skill workflow no longer
needs to launch a separate Codex CLI process. Codex reviews the source-backed
artifacts in the current session and writes JSON Review/Patch files directly.
Scripts then validate and apply the patches.

## 2. Responsibility Boundary

Scripts remain deterministic and own:

- AST extraction and stable `fact_id`;
- Semantic Inventory;
- baseline Architecture IR;
- schema contracts;
- patch application;
- validators;
- Diagram View, layout and renderer;
- review lock and reproducibility.

Codex owns reviewed-mode judgment:

- fact dispositions;
- aggregation of low-level facts;
- direct/derived/external classification;
- semantic findings;
- visual findings;
- view patch recommendations.

Codex still cannot directly modify final Architecture IR, Diagram View or
Draw.io XML. All changes pass through Review JSON, Patch JSON, validators and
apply scripts.

## 3. Semantic Review Flow

In the default interactive workflow, VSCode Codex reads
`review/prompts/semantic_review.md`, the source file, source-analysis,
inventory, baseline IR and baseline coverage, then writes:

- `semantic-review.json`
- `architecture-ir.patch.json`

The scripts do not trust the Agent output blindly. `validate_semantic_review.py`
checks dispositions, fact IDs, finding handling, patch hashes and forbidden
evidence changes before `apply_ir_patch.py` can create the reviewed IR.

`run_semantic_review.py` remains in the repository as an optional automation
helper and test harness. It can consume a mock response or be wired into a
future non-interactive integration, but it is not the default VSCode Skill path.

## 4. Visual Review Flow

In the default workflow, VSCode Codex reads the reviewed IR, baseline Diagram
View, baseline layout metrics and `review/prompts/visual_review.md`, then
writes:

- `visual-review.json`
- `diagram-view.patch.json`

Visual Patch validation forbids semantic changes such as adding/deleting nodes
or edges, changing endpoints, changing phase or changing evidence.

`run_visual_review.py` is likewise optional automation. It is useful for tests
with mocked JSON responses, but the reviewed Skill flow is intentionally simpler:
current Codex judgment writes patch artifacts; deterministic scripts enforce the
boundary.

## 5. Patch Mechanism

Architecture IR Patch remains schema `0.1`. In the HY V3 v0.9.1 run, the final
patch contains 1 operation:

- resolve baseline `external_config_values` unresolved bucket after Codex
  classified symbolic configuration facts.

Diagram View Patch contains 5 operations from Codex Visual Review. All are
presentation-only and passed validation.

## 6. Validator Anti-Hallucination Controls

Semantic Review Validator checks:

- every required fact has exactly one disposition;
- fact IDs and supporting fact IDs exist;
- aggregation targets exist in IR or patch-added IDs;
- documented external dispositions name an external symbol;
- patch hashes match;
- behavior patches cannot use import-only evidence;
- major findings are patched or deferred;
- mass exclusion is rejected.

Visual Review Validator checks:

- patch hash matches baseline View;
- all referenced IDs exist;
- semantic operations are forbidden;
- optional/external correctness labels cannot be hidden by patch.

## 12. Current Limits

The integration now uses real Codex judgment in reviewed mode, but CI uses saved
or mocked Review/Patch artifacts for reproducibility. The default VSCode flow
avoids a nested Codex CLI call; optional runners remain available for future
automation and mock-based tests.

The project still does not recursively analyze external vLLM components and does
not claim general support for all vLLM model adapters.
