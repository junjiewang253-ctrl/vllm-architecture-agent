# v0.4 Implementation Report

## 1. 本次任务目标

v0.4 的目标是把 Skill 的中间表示从手写、自由发挥的 Architecture IR，推进到可由 source-analysis JSON 自动生成草稿、再由 Agent 审查补充的流程。

本次实现聚焦四件事：

- 将 Architecture IR schema 升级到 `0.2`。
- 新增 `build_architecture_ir.py`，从 `source-analysis.json` 生成 Overview 级别的 `architecture-ir.json` 草稿。
- 增强 `validate_architecture_ir.py`，加入 phase、scope、parent、repetition、variant、badge、跨 scope edge 等语义校验。
- 更新 Skill 工作流，并为 v0.4 变更补充测试和实验输出。

本次明确没有实现完整 Draw.io Renderer、`validate_drawio.py`、Attention/MoE/Weight Mapping 详情页、Claude Code 插件、Codex 插件打包或自动下载 vLLM 源码。

## 2. 修改前存在的问题

旧 Architecture IR 是 `0.1`，它能表达基础节点和边，但对复杂 vLLM adapter 的语义边界不够明确。

旧 IR 不够准确的主要原因：

- 节点缺少 `phase`，无法区分构造阶段、运行时、checkpoint loading 和 parallel partition。
- 节点缺少 `scope`，无法表达某个节点属于 `HYV3Model.forward`、`HYV3DecoderLayer.forward` 还是 `HYV3ForCausalLM.compute_logits`。
- 节点缺少 `parent_id`，只能用 containment edge 表达容器关系，容易把容器误看成普通 tensor-flow 节点。
- 重复层只有旧的字符串 `repeat`，无法保留 `config.num_hidden_layers`、`self.start_layer`、`self.end_layer` 这些结构化信息。
- Dense FFN / MoE 选择曾被画成 runtime decision，但 HY V3 源码里的 `layer_idx < config.first_k_dense_replace` 出现在 `HYV3DecoderLayer.__init__`，这是构造阶段的层类型选择，不是 forward 时每次 token flow 都动态分支。
- Agent 需要自由手写 `architecture-ir.json`，容易漏证据、混淆 checkpoint mapping 和 runtime flow，或根据模型常识补出源码中没有的结构。

Dense/MoE 不应该画成 runtime decision：

- 源码行 395 的条件在 `__init__` 中执行。
- true 分支构造 `HYV3FeedForward`，false 分支构造 `HYV3MoEFused`。
- `forward` 中只调用 `self.mlp(hidden_states)`，并没有再次判断 Dense 或 MoE。
- 因此 v0.4 把它记录为 repeated decoder node 的 `variants`，每个 variant 的 `phase` 都是 `construction`。

需要 `phase`、`scope` 和 `parent_id` 的原因：

- `phase` 防止 checkpoint weight mapping 被混入 runtime tensor flow，也防止 construction-only 结构被 runtime edge 连接。
- `scope` 让校验器能发现跨函数/跨模块的 runtime edge。例如 `HYV3Model.forward` 的 final norm 结果进入 `HYV3ForCausalLM.compute_logits`，这不是同一 scope 内的普通 runtime edge，应该用 `summary` 表达。
- `parent_id` 让 `HYV3Attention` 可以明确属于 repeated `HYV3DecoderLayer`，而不需要把容器节点画成可计算 tensor-flow 节点。

需要自动构建 IR 的原因：

- source-analysis JSON 已经有类、模块赋值、make_layers、控制流、条件、并行 hints 和权重映射等事实。
- 自动 builder 可以稳定产出草稿，减少 Agent 手写 IR 的不一致。
- Agent 后续只需要检查 `unresolved`，并在证据支持时补充或修正。

## 3. 技术方案

### Architecture IR 0.2 数据结构

顶层仍保留：

- `schema_version`
- `model_name`
- `detail_level`
- `pages`
- `unresolved`

`schema_version` 从 `0.1` 升级为 `0.2`。

Node 支持：

- `id`
- `label`
- `subtitle`
- `kind`
- `phase`
- `scope`
- `parent_id`
- `badges`
- `repetition`
- `variants`
- `evidence`

Edge 支持：

- `id`
- `source`
- `target`
- `kind`
- `phase`
- `scope`
- `label`
- `condition`
- `source_port`
- `target_port`
- `evidence`

Edge kind 保留原有类型，并新增 `invocation` 和 `summary`。

### phase 设计

合法 phase：

- `construction`
- `runtime`
- `checkpoint_loading`
- `parallel_partition`

v0.4 中 Overview 主要节点通常是 runtime 抽象节点，但 Dense/MoE variant 必须是 `construction`。`weight_mapping` edge 必须使用 `checkpoint_loading`。

### scope 设计

`scope` 使用字符串保存节点或边所属代码范围，例如：

- `HYV3Model.forward`
- `HYV3DecoderLayer.forward`
- `HYV3Attention.forward`
- `HYV3ForCausalLM.compute_logits`

Validator 规则是：普通 `runtime` edge 默认不能跨不同 scope。跨 scope 连接必须用 `invocation` 或 `summary`，这能防止把函数调用、返回值汇总和同一函数内部 tensor flow 混为一谈。

### parent_id 设计

`parent_id` 表示节点所属容器。例如 v0.4 HY V3 输出中：

- `hyv3_model.parent_id = hyv3_for_causal_lm`
- `vocab_parallel_embedding.parent_id = hyv3_model`
- `hyv3_decoder_layer.parent_id = hyv3_model`
- `hyv3_attention.parent_id = hyv3_decoder_layer`
- `lm_head.parent_id = hyv3_for_causal_lm`
- `logits_processor.parent_id = hyv3_for_causal_lm`

Validator 会检查 parent 节点存在，并禁止节点把自己作为 parent。

### repetition 和 variants 设计

旧的 `repeat` 字符串被替换为：

```json
{
  "count_expression": "config.num_hidden_layers",
  "local_start": "self.start_layer",
  "local_end": "self.end_layer"
}
```

这保留了 pipeline parallel local layer slice 的源码信息。Validator 会要求 `count_expression` 非空。

Dense/MoE 选择记录为：

```json
[
  {
    "condition": "layer_idx < config.first_k_dense_replace",
    "component": "HYV3FeedForward",
    "phase": "construction"
  },
  {
    "condition": "layer_idx >= config.first_k_dense_replace",
    "component": "HYV3MoEFused",
    "phase": "construction"
  }
]
```

### port 设计

Edge 的 `source_port` 和 `target_port` 用于表达多输入调用中的参数角色。例如 LogitsProcessor 有两类输入：

- hidden states 进入 `target_port: hidden_states`
- LM Head 作为 dependency 进入 `target_port: lm_head`

这为后续 renderer 布局和端口连接预留确定性信息。

### build_architecture_ir.py 整体流程

Builder 输入 source-analysis JSON，输出 Overview Architecture IR。

主要步骤：

1. 校验 source-analysis `schema_version` 必须是 `0.2`。
2. 根据类名后缀、子模块赋值和 `forward` 中 `self.model` 调用识别顶层 ForCausalLM。
3. 从顶层类的 `self.model` assignment 找到内部模型类。
4. 在内部模型类中识别 embedding、`make_layers`、final norm。
5. 从 `layer_factories[].layer_constructor` 找到 decoder layer 类。
6. 在 decoder layer 中识别 Attention assignment。
7. 在 decoder layer `__init__` 的 `conditions` 中识别 `layer_idx < config.first_k_dense_replace`，生成 construction variants。
8. 根据 `parallelism_hints` 为节点添加 TP、PP、EP badges。
9. 为外部 `config.*` 表达式生成 `unresolved`。
10. 生成带 evidence 的 nodes 和 edges。

### Validator 新增语义检查

v0.4 validator 新增或强化：

- `schema_version` 必须是 `0.2`。
- node `phase` 必须合法。
- edge `phase` 必须合法。
- `parent_id` 引用必须存在。
- 节点不能把自己作为 parent。
- runtime edge 不能跨不同 scope。
- 跨 scope edge 必须使用 `invocation` 或 `summary`。
- construction phase node 不能使用 runtime edge。
- Dense/MoE variants 必须是 construction phase。
- `weight_mapping` edge 必须是 checkpoint_loading phase。
- residual edge 必须指向 `add` 或 `merge`。
- 每个 major node 必须有 evidence。
- Overview 页面最多 12 个 major nodes。
- `repetition.count_expression` 不得为空。
- badges 只能使用 `TP`、`PP`、`EP`。

Validator 会一次输出所有发现的问题，而不是遇到第一个错误就退出。

## 5. 关键实现说明

### `build_architecture_ir(data)`

输入：

- source-analysis JSON 解析后的 `dict[str, Any]`。

输出：

- Architecture IR `0.2` 的 `dict[str, Any]`。

核心逻辑：

- 校验 source-analysis version。
- 调用一组识别函数找到顶层 ForCausalLM、内部模型、embedding、decoder factory、final norm、LM Head、LogitsProcessor、Attention 和 Dense/MoE variants。
- 组装 Overview nodes 和 edges。
- 为 runtime、invocation、summary、dependency、residual edge 设置 phase、scope 和 evidence。
- 收集 `config.*` 外部表达式进入 `unresolved`。

已知限制：

- 只生成 Overview 页面。
- 只覆盖常见 vLLM 模式。
- `compute_logits` 的调用体目前主要通过 assignment 和 method line 作为证据，因为 extractor 只完整结构化 `forward` 和 `load_weights`。
- 不读取外部 config 文件，也不推断具体数值。

### `_find_top_level_class(data, unresolved)`

输入：

- source-analysis JSON。
- unresolved 列表。

输出：

- 唯一顶层 ForCausalLM 类名，或 `None`。

核心逻辑：

- 优先选择类名以 `ForCausalLM` 结尾的类。
- 根据是否有 `model`、`lm_head`、`logits_processor` submodule 加分。
- 根据 `forward` 中是否调用 `self.model` 加分。
- 如果最高分不唯一，则写入 `unresolved` 而不猜测。

已知限制：

- 对不以 `ForCausalLM` 结尾的特殊 adapter 暂不自动识别。

### `_find_dense_moe_variants(data, decoder_class)`

输入：

- source-analysis JSON。
- decoder layer 类名。

输出：

- `variants` 列表和相关证据 records。

核心逻辑：

- 查找 decoder `__init__` 中包含 `layer_idx` 和 `first_k_dense_replace` 的 condition。
- true branch 的 `self.mlp` assignment 变成第一个 construction variant。
- false branch 的 `self.mlp` assignment 变成第二个 construction variant。
- 对 `<` 条件生成对应的 `>=` 反向条件。

已知限制：

- 目前只支持 `self.mlp` 上的 Dense/MoE 构造选择。
- 对更复杂的多层 condition 或非 `layer_idx` 模式会保留 unresolved。

### `_badges_for_contexts(data, contexts, include_nested=False)`

输入：

- source-analysis JSON。
- 上下文名列表，例如 `HYV3Attention.__init__`。

输出：

- `TP`、`PP`、`EP` badge 列表。

核心逻辑：

- 从 `parallelism_hints` 按 context 收集 symbol。
- `QKVParallelLinear`、`RowParallelLinear`、`VocabParallelEmbedding`、`ParallelLMHead` 生成 TP。
- `get_pp_group`、`make_layers`、`PPMissingLayer` 生成 PP。
- `get_ep_group`、`FusedMoE` 生成 EP。

已知限制：

- badge 是保守摘要，不表达具体并行维度和 rank 分配。

### `validate_architecture_ir(data)`

输入：

- Architecture IR JSON 解析后的 `dict[str, Any]`。

输出：

- 错误字符串列表。空列表表示通过。

核心逻辑：

- 先做基础结构检查：version、model_name、detail_level、pages、nodes、edges。
- 建立 node id 索引用于 endpoint 和 parent 检查。
- 检查 node phase、badge、repetition、variants、evidence。
- 检查 edge endpoint、kind、phase、evidence、scope crossing、weight mapping phase、residual target。
- Overview 统计 major node 数量，限制最多 12 个。

已知限制：

- Validator 不加载 JSON schema 文件，而是使用内置语义规则。
- 对 renderer 布局、Draw.io XML ID 一致性和可视化重叠没有校验，这些留给 v0.5。

### `outputs/hy-v3-architecture-ir.json`

生成结果：

- `schema_version`: `0.2`
- 页面数：1
- 页面 ID：`overview`
- nodes：10
- edges：9

节点 ID：

- `hyv3_for_causal_lm`
- `hyv3_model`
- `input`
- `vocab_parallel_embedding`
- `hyv3_decoder_layer`
- `hyv3_attention`
- `final_residual_add`
- `norm`
- `lm_head`
- `logits_processor`

顶层模型如何识别：

- `HYV3ForCausalLM` 类名以 `ForCausalLM` 结尾。
- 类中包含 `self.model`、`self.lm_head`、`self.logits_processor`。
- `forward` 中调用 `self.model(...)`。
- 因此 builder 唯一选中 `HYV3ForCausalLM`。

Decoder Layer 如何识别：

- `HYV3Model.__init__` 的 `make_layers` 被 extractor 记录到 `layer_factories`。
- `layer_constructor` 是 `HYV3DecoderLayer`。
- `HYV3Model.forward` 中 loop 调用 `layer(...)`，并且 `resolved_collection` 是 `self.layers`。
- Builder 将其生成 repeated block node：`hyv3_decoder_layer`。

repetition 如何生成：

- `count_expression` 来自 `layer_factories[].repeat_expression`，值为 `config.num_hidden_layers`。
- `local_start` 固定记录为 `self.start_layer`。
- `local_end` 固定记录为 `self.end_layer`。

Dense/MoE variants 如何生成：

- Builder 在 `HYV3DecoderLayer.__init__` conditions 中找到 `layer_idx < config.first_k_dense_replace`。
- true branch `self.mlp = HYV3FeedForward(...)` 生成 construction variant。
- false branch `self.mlp = HYV3MoEFused(...)` 生成 construction variant。
- 没有生成 runtime decision node。

TP/PP/EP badges 如何生成：

- `vocab_parallel_embedding` 因 `VocabParallelEmbedding` 标记 TP。
- `hyv3_attention` 因 `QKVParallelLinear` 和 `RowParallelLinear` 标记 TP。
- `lm_head` 因 `ParallelLMHead` 标记 TP。
- `hyv3_decoder_layer` 因 `make_layers`、`PPMissingLayer`、`get_pp_group` 标记 PP。
- `hyv3_decoder_layer` 同时因 MoE construction variant 和 `FusedMoE`/`get_ep_group` 相关 evidence 摘要标记 EP。

unresolved 中还剩什么：

- `external_config_values`
- expressions：
  - `config.first_k_dense_replace`
  - `config.hidden_act`
  - `config.hidden_size`
  - `config.intermediate_size`
  - `config.num_hidden_layers`
  - `config.rms_norm_eps`
  - `config.vocab_size`

这些都是源码中的外部配置表达式，v0.4 不会从缺失 config 文件推断具体值。

## 8. 当前限制

- 只支持 Overview 页面。
- 模型模式规则仍有限，主要覆盖常见 ForCausalLM + self.model + make_layers 模式。
- Dense/MoE variant 识别目前聚焦 `layer_idx < config.first_k_dense_replace` 和 `self.mlp`。
- Agent 仍可能需要查看 `unresolved` 并在证据支持时修正 IR。
- 尚未实现确定性 Draw.io Renderer。
- 尚未实现 Draw.io XML validator。
- 尚未实现 Attention、MoE、Weight Mapping 详情页。
- `compute_logits` 还没有像 `forward` 那样被 extractor 完整结构化，当前 builder 使用 method line 和 assignment evidence 表达 LogitsProcessor 关系。

## 9. 下一步建议

v0.5 建议聚焦确定性渲染链路：

- 实现 `render_drawio.py`，将 Architecture IR 0.2 忠实渲染为 Draw.io XML。
- 实现 `validate_drawio.py`，检查 Draw.io XML 中的节点/edge ID 和 IR 一致。
- 定义 IR node/edge ID 到 Draw.io cell ID 的稳定映射。
- 支持多页面渲染：Overview、Attention Detail、MoE Detail、Weight Mapping Detail。
- 加入基础节点布局策略，避免节点重叠和 edge 路径混乱。
- 在 renderer 中支持 `parent_id` 容器、badges、ports、repetition 和 variants 的可视化。
