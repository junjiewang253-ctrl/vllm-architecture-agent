# v1.1 Architecture Designer Implementation Report

## 1. Task Goal

v1.1 fixes the remaining v1.0/v1.0.2 weakness: the system had a Source Fact
Graph and an Architecture Concept Graph, but the View layer was still too close
to a direct concept projection. That made diagrams look like concept cards
rather than architecture diagrams with a story, data flow, module interaction
and external boundaries.

The new target pipeline is:

```text
Python source
-> Source Fact Graph
-> Architecture Concept Graph
-> Architecture Design Graph
-> Architecture View Graph
-> Deterministic Draw.io Renderer
```

## 2. Why Concept Layer Was Not Enough

Concepts answer "what does this set of source facts mean?" For example,
`QKVParallelLinear`, tensor-parallel metadata and attention head partitioning
can become the concept "Tensor Parallel QKV Projection".

That is useful for architecture understanding, but it is not enough to draw a
professional diagram. A page must answer a reader-facing question such as "How
does HYV3 attention adapt to the vLLM attention backend?" That requires a main
flow, branches, boundaries and decisions about whether TP/EP/LoRA are shown as
nodes, badges or annotations. Rendering concepts directly collapses all of
those decisions into rectangular explanation cards.

## 3. Architecture Design Layer

The new Architecture Design Graph is a blueprint for drawing, not the final
diagram. Each page contains:

- `question`: the human question answered by the page.
- `purpose`: a short narrative goal.
- `main_flow`: ordered semantic IDs that form the primary reading path.
- `branches`: optional or secondary flows such as HPC/fallback attention paths.
- `external_boundaries`: imported runtime behavior that must not be claimed as
  locally proven.
- `nodes` and `edges`: source-backed drawing candidates with roles.

The Design layer separates "Agent understanding" from "renderer syntax". It
also prevents the renderer from interpreting concepts on its own.

## 4. Agent Design Workflow

`run_architect_review.py` still creates the Architecture Concept Graph from the
Source Fact Graph. v1.1 adds `run_design_architect.py`, which creates the
Architecture Design Graph from concepts and source facts.

The design architect decides:

- which page question is worth answering;
- which concepts become primary flow components;
- which concepts become secondary branches or strategy annotations;
- which edges are runtime flow, mapping, dependency, parallel or boundary;
- which external behavior remains a boundary.

The current implementation is deterministic and source-grounded for HY V3, but
the separation is the important interface for future Agent-driven design.

## 5. View Generator

`build_view_from_design.py` is intentionally mechanical. It copies the Design
Graph's page story into the renderer-facing Architecture View Graph:

- Design node `role` becomes View node `role` and `visual_role`.
- Design node `concept_refs` and `fact_refs` are preserved.
- Design edge type/source/target/ports/labels are preserved.
- Page `main_flow`, `branches` and `external_boundaries` remain available for
  validators and reports.

The generator does not create new semantic concepts and does not infer model
behavior.

## 6. Renderer Changes

The renderer still reads Architecture View Graph plus Layout Plan. It does not
read Architecture Concept Graph in architect mode. This preserves a clean
boundary:

- Concept Graph: source-backed architecture meaning.
- Design Graph: page story and explanatory structure.
- View Graph: renderable architecture nodes and edges.
- Renderer: deterministic geometry, styles and Draw.io XML.

## 7. Validator Changes

`validate_architecture_view.py` now rejects common concept-card regressions:

- a page with fewer than three `primary_flow` nodes;
- a page made only of annotations;
- a page where all visible roles look like concept cards;
- pages where all edges are annotations;
- Attention pages missing QKV Projection, Q/K/V, HPC fused path, Optional QK
  Norm, KV Cache Boundary or vLLM Attention Backend;
- MoE pages missing Router, Top-K Selection, FusedMoE, Experts, Shared Experts
  or Expert Parallel;
- Checkpoint pages missing HF Checkpoint, Weight Name Processing, Mapping,
  qkv/FusedMoE parameter targets, Loader or vLLM Parameters;
- Boundary pages missing Local Adapter, Adapter Boundary or External vLLM
  Runtime.

`validate_architecture_quality.py` was updated to expect the v1.1 page titles:
Model Overview, Attention Implementation, MoE Execution, Parallel Strategy,
Weight Adaptation and vLLM Boundary.

## 8. Page Design

### Model Overview

Answers: How does HYV3 run inside vLLM?

Main flow:

```text
Input IDs / Embeds -> Embedding -> Decoder Stack -> Final Norm
-> Hidden States -> Logits Processor -> Logits
```

LM Head is a dependency into Logits Processor. TP/PP/EP is a strategy
annotation, not a runtime flow node.

### Attention Implementation

Answers: How does HYV3 attention adapt HF-style attention to the vLLM backend?

Main flow:

```text
Hidden States -> QKV Projection -> Q/K/V Split
-> vLLM Attention Backend -> Output Projection -> Attention Output
```

Branches:

- HPC fused path from QKV Projection to vLLM Attention Backend.
- Fallback path through Q, K, V, Optional QK Norm and RoPE Processing.
- KV Cache is shown as an external boundary, not a local direct implementation.

### MoE Execution

Answers: How does HYV3 route tokens through experts?

Main flow:

```text
Hidden States -> Router -> Top-K Selection -> FusedMoE -> Experts -> Output
```

Shared Experts and Expert Parallel are secondary/strategy relationships, not a
fake serial runtime chain.

### Weight Adaptation

Answers: How do HF checkpoint weights become vLLM parameters?

Main flow:

```text
HF Checkpoint -> Weight Name Processing -> Mapping -> Loader -> vLLM Parameters
```

Mapping branches show q/k/v to `qkv_proj`, gate/up to `gate_up_proj`, and expert
weights to FusedMoE parameters.

### Parallel Strategy

Answers: How are TP, PP and EP organized independently?

TP, PP and EP are independent primary regions. The page explicitly avoids a
false `TP -> PP -> EP` serial chain.

### vLLM Boundary

Answers: Where does local adapter code stop and imported vLLM runtime behavior
begin?

Local adapter nodes are separated from external vLLM runtime nodes by an
Adapter Boundary. External Attention, FusedMoE and AutoWeightsLoader internals
remain boundary claims.

## 13. v1.0 vs v1.1

v1.0/v1.0.2 separated concepts from views, but the View layer could still act
like a direct concept translation. v1.1 makes the missing layer explicit:
Design decides the page story before View nodes exist.

This changes the diagram from "cards describing concepts" toward "pages that
answer architecture questions".

## 14. Current Limits

- The Design Architect implementation is still deterministic and tuned around
  the available HY V3 concept set.
- The project does not recursively analyze imported vLLM implementation files.
- Renderer layout remains lightweight and deterministic, not a general graph
  layout engine.
- The old v0.9.1 IR/Diagram View path remains for regression compatibility.

## 15. Next Steps

For v1.2, the most useful next step is to make `run_design_architect.py` a true
Agent-guided design interface that emits the same Design Graph schema, then let
validators enforce evidence, boundary and view-quality constraints. After that,
run the same flow against a second vLLM model adapter to test whether the
Concept -> Design -> View split generalizes.
