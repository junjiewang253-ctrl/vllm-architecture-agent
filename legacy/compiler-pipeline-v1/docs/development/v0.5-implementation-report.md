# v0.5 Implementation Report

## 1. 任务目标

v0.5 要解决的问题是：Draw.io XML 不能再由 Agent 临时手写或自由解释架构，而必须由确定性 Renderer 从 Architecture IR 生成。

目标流程改为：

```text
Python source
-> source-analysis.json
-> architecture-ir.json
-> render_drawio.py
-> .drawio
-> validate_drawio.py
-> Draw.io MCP 打开和导出
```

本次重点完成：

- IR node 与 Draw.io semantic node 一一对应。
- IR edge 与 Draw.io semantic edge 一一对应。
- `parent_id` 映射为 Draw.io `parent`。
- container 和 repeated block 真正作为容器渲染。
- construction variants、TP/PP/EP badges 作为 `decorative_` cell 渲染。
- 同一 IR 多次渲染输出字节级一致。
- Draw.io MCP 只负责打开、查看和导出，不再重新解释架构。

## 2. 修改前的问题

v0.4 已经在 Architecture IR 中加入了 `parent_id`，但 Draw.io 阶段仍没有确定性实现。旧流程的问题是：

- IR 里已有 parent 层级，但旧 Draw.io XML 可能仍让所有节点使用 `parent="1"`。
- container 节点容易被画成普通小方框，而不是包围子节点的架构容器。
- repeated block 也容易被画成普通节点，无法容纳 Attention 和 construction variants。
- Agent 手写 XML 会导致 IR 与 Draw.io 漂移，例如漏节点、漏边、增加额外语义说明、改错 edge source/target。
- 每次生成 XML 的布局、ID 和样式可能不一致，难以回归测试。

因此 v0.5 增加确定性 Renderer 和 Draw.io Validator。Renderer 严格以 IR 为唯一语义来源；Validator 再反向检查 `.drawio` 是否忠实保存了 IR 语义。

## 3. 技术方案

### Renderer 整体架构

`render_drawio.py` 分为三层：

- 样式配置：`NODE_STYLES`、`EDGE_STYLES`。
- 布局计算：`LayoutBox`、`Decoration`、`compute_layout()` 和容器布局函数。
- XML 生成：`render_drawio()` 将 layout 和 IR 转成 Draw.io `<mxfile>`。

Renderer 只生成 Overview 页面，不读取源码，不重跑模式识别，不根据模型常识补节点。

### node style 映射

`NODE_STYLES` 集中定义不同 `kind` 的 Draw.io 样式，至少覆盖：

- `container`
- `input`
- `embedding`
- `repeated_block`
- `attention`
- `normalization`
- `add`
- `head`
- `logits_processor`
- `ffn`
- `moe`
- `note`

所有样式都使用：

- `html=0`
- `whiteSpace=wrap`
- 统一字体 `Inter`

节点标题由 `label` 和 `subtitle` 分行组成，不显示 evidence 行号。

### edge style 映射

`EDGE_STYLES` 集中定义不同 edge kind：

- `runtime`：实线箭头。
- `residual`：较粗实线箭头，默认 label 为 `residual`。
- `dependency`：虚线/open arrow。
- `invocation`：虚线箭头。
- `summary`：较粗实线箭头。
- `containment`：很浅的虚线，主要语义由 `parent_id` 表达。
- `weight_mapping`：点划线。
- `conditional_true` / `conditional_false`：带 true/false 默认 label。

当前 HY V3 Overview 没有 runtime Dense/MoE conditional edge，因为 Dense/MoE 已经是 construction variants。

### parent_id 转换

Renderer 的 `_node_parent()` 规则：

- `parent_id == null`：Draw.io parent 为 `1`。
- `parent_id != null`：Draw.io parent 等于 IR 中的父节点 ID。

HY V3 中生成的关键 parent：

- `hyv3_model.parent = hyv3_for_causal_lm`
- `input.parent = hyv3_model`
- `vocab_parallel_embedding.parent = hyv3_model`
- `hyv3_decoder_layer.parent = hyv3_model`
- `hyv3_attention.parent = hyv3_decoder_layer`
- `lm_head.parent = hyv3_for_causal_lm`
- `logits_processor.parent = hyv3_for_causal_lm`

子节点坐标相对于父容器，Validator 会检查子节点不超出父容器范围。

### container 尺寸计算

Renderer 先递归计算子节点尺寸，再从最深层向外计算父容器尺寸。

主要规则：

- container 预留标题高度 `TITLE_HEIGHT`。
- 子节点与容器边界之间预留 `PADDING`。
- 子节点之间使用固定 `GAP`。
- 顶层 container 如果同时包含大容器和叶子节点，则将大容器放左侧，叶子节点在右侧竖排。
- 普通 container 内部按 IR 节点顺序横向排列。

这保证 HY V3 Overview 中：

```text
HYV3ForCausalLM
├── HYV3Model
│   ├── Input
│   ├── VocabParallelEmbedding
│   ├── HYV3DecoderLayer
│   │   └── HYV3Attention
│   ├── Add Residual
│   └── RMSNorm
├── ParallelLMHead
└── LogitsProcessor
```

### repeated block 渲染

`kind == "repeated_block"` 使用容器样式，而不是普通节点样式。

标题由 `_node_label()` 生成：

```text
config.num_hidden_layers x HYV3DecoderLayer
local range: self.start_layer -> self.end_layer
```

其内部放置：

- semantic child node，例如 `hyv3_attention`。
- construction variants decorative cell。
- badges decorative cell。

### variants 渲染

`variants` 不生成语义 node，也不生成 runtime decision edge。

Renderer 生成：

```text
decorative_variants_<node_id>
```

HY V3 中是：

```text
decorative_variants_hyv3_decoder_layer
```

内容包含：

```text
Construction variants
layer_idx < config.first_k_dense_replace -> HYV3FeedForward
layer_idx >= config.first_k_dense_replace -> HYV3MoEFused
```

### badge 渲染

每个 badge 生成一个 decorative cell：

```text
decorative_badge_<node_id>_<badge>
```

例如：

- `decorative_badge_hyv3_attention_TP`
- `decorative_badge_hyv3_decoder_layer_EP`

Badge cell parent 是对应语义 node，因此它们贴在节点内部右上角，不计入语义节点数量。

### 布局算法

当前是 Overview 专用分层布局，不是通用自动布局算法。

顺序：

1. 读取 IR page。
2. 根据 `parent_id` 建立树。
3. 递归测量叶子节点。
4. 测量 repeated block，并放入 variants decorative cell。
5. 测量普通 container。
6. 放置 root containers。
7. 生成 nodes。
8. 生成 edges。
9. 生成 decorations。

布局不使用随机数，不依赖偶然遍历顺序，所有节点顺序来自 IR 中的数组顺序。

### XML 生成方式

Renderer 使用 Python 标准库 `xml.etree.ElementTree` 生成 XML。

输出结构：

```xml
<mxfile>
  <diagram id="overview" name="Overview">
    <mxGraphModel>
      <root>
        <mxCell id="0"/>
        <mxCell id="1" parent="0"/>
        ...
      </root>
    </mxGraphModel>
  </diagram>
</mxfile>
```

为了稳定性，`modified` 等 mxfile 属性使用固定值，不写入当前时间。

### Draw.io Validator 检查逻辑

`validate_drawio.py` 以 IR 为真值表，检查：

- 每个 IR node ID 在 Draw.io 中存在。
- 每个 IR edge ID 在 Draw.io 中存在。
- Draw.io 中没有额外 semantic node。
- Draw.io 中没有额外 semantic edge。
- `decorative_` 前缀 cell 不计入语义。
- edge source 与 IR 一致。
- edge target 与 IR 一致。
- node parent 与 IR `parent_id` 一致。
- 有 `parent_id` 的节点不能仍然使用 root parent。
- semantic node 必须有 geometry。
- semantic node 宽高必须大于 0。
- 子节点必须位于父容器范围内。
- XML 必须能解析。

失败时一次输出所有问题并返回非零退出码。成功时输出：

```text
Draw.io validation passed
```

## 5. 关键函数说明

### `render_drawio(ir)`

输入：

- Architecture IR `dict[str, Any]`。

输出：

- Draw.io XML 字符串。

核心算法：

- 遍历 IR pages。
- 调用 `compute_layout()` 获取每个 semantic node 的 `LayoutBox` 和 decorations。
- 生成 root sentinel cells。
- 按 IR node 数组顺序生成 semantic vertex cells。
- 按 IR edge 数组顺序生成 semantic edge cells。
- 生成 title、variants、badges 等 decorative cells。

已知限制：

- 当前只优化 Overview。
- 不支持复杂多页面布局。
- edge route 依赖 Draw.io 的 orthogonal routing。

### `compute_layout(page)`

输入：

- 单个 IR page。

输出：

- `dict[str, LayoutBox]`
- `list[Decoration]`

核心算法：

- 以 `parent_id` 建立隐式树。
- 从 root node 开始递归 `_measure_node()`。
- root node 使用绝对 page 坐标。
- child node 使用相对父容器坐标。

已知限制：

- 没有做通用碰撞避让。
- 布局策略针对 Transformer Overview。

### `_layout_container(...)`

输入：

- 当前 container node。
- 已测量的 child boxes。

输出：

- 当前 container 的 `LayoutBox`。

核心算法：

- 如果是顶层 container 且同时有子容器和叶子节点，则子容器左侧、叶子节点右侧竖排。
- 否则子节点按 IR 顺序横向排列。
- 按 child bounds 加 padding 和 title height 得到父容器尺寸。

已知限制：

- 对非常多子节点的容器尚未自动换行。

### `_layout_repeated_block(...)`

输入：

- repeated block node。
- child boxes。

输出：

- repeated block `LayoutBox`。

核心算法：

- 子节点在容器内纵向排列。
- 根据 `variants` 创建 `decorative_variants_<node_id>`。
- repeated block 尺寸包住 semantic children 和 variants decorative cell。

已知限制：

- variants 使用文本说明，尚未图形化为 mini table 或 timeline。

### `_node_label(node)`

输入：

- IR node。

输出：

- Draw.io cell value。

核心算法：

- 普通节点使用 `label` 和 `subtitle`。
- repeated block 使用 `repetition.count_expression` 改写标题，并显示 `local_start -> local_end`。

已知限制：

- 不做长文本自动缩略。

### `validate_drawio(ir, drawio_path)`

输入：

- Architecture IR。
- `.drawio` 文件路径。

输出：

- 错误字符串列表。

核心算法：

- 解析 Draw.io XML。
- 收集 semantic nodes 和 edges。
- 对照 IR 检查缺失和多余。
- 检查 edge source/target。
- 检查 node parent。
- 检查 geometry 和容器范围。

已知限制：

- 只校验 XML 结构和语义一致性，不检查视觉美学。
- 不解码 diagrams.net 压缩格式；v0.5 renderer 输出 plain XML。

## 9. 当前限制

- 当前只优化 Overview。
- 布局规则仍针对常见 Transformer Overview。
- 还没有通用自动布局算法。
- 尚未支持复杂多页面。
- 尚未支持 Attention、MoE、Weight Mapping 详情页。
- `validate_drawio.py` 不校验视觉美学，只校验语义一致性和基础几何。
- MCP 导出 SVG 可能仍存在 diagrams.net 兼容问题，本次只确认导出成功。
